This is the API reference for Tsuchi. The API is organized into services, and the services
are grouped into three layers. Pick a service below to see its functions, events, and types.

In Lua and JavaScript, services are globals, like `mod.id`. Lua subscribes with
`time.on_step`, while JavaScript uses `time.on("step", callback)`. In C and C++, use
the host, like `host->time` or `host->mod`.

Lua represents structs and lists as tables, and bytes as strings. JavaScript uses
objects, Arrays, and `Uint8Array`. JavaScript `u64` and `i64` values are BigInt, so
all 64 bits survive. Handles are opaque values whose identity stays stable while
your script holds them.

## Scope

Use the layers below to choose the systems your mod needs. You can combine scripts,
compiled code, cooked Blueprints, and generated Tsuchi Blueprint nodes, and publish
services for other mods to use across languages.

Services and parts marked Coming soon aren't in Tsuchi yet. Tsuchi's Blueprint nodes and published services are coming soon too.

### Core

| Service | Covers |
| --- | --- |
| `mod` | Mod identity and versions, and logging. <Badge text="Coming soon" variant="note" /> Publishing or finding shared services. |
| `settings` | Typed player settings, with change events. Players change them on the **Mods** page. |
| `file` | Reading and listing your mod's files. |
| `storage` | Saving, loading, listing, and removing your mod's own data. |
| `time` | World steps, presented pictures, and frame-rate requests. <Badge text="Coming soon" variant="note" /> Timers. |
| `hook` | Wrapping named game functions, calling the original, and chaining with other mods. |
| `net` | UDP sockets and HTTPS requests. |
| `session` | Hosting or joining multiplayer, peers, per-mod channels, and a shared clock. |

## Results

Every function returns a result. If the result is anything other than `ok`, the call didn't
change anything.

In C, functions return a `TSUCHI_Result`, like `TSUCHI_NOT_FOUND`. In Lua, a function that
fails returns `nil` followed by the name of the result. If you pass an invalid argument in
Lua, the function raises an error instead. JavaScript failures throw an `Error`
whose `name` is the result code and whose `message` describes the failure. Invalid
JavaScript arguments raise a type or range error. Functions that wait return a
Promise in JavaScript, so use `await` as their reference describes.

| Result | Meaning |
| --- | --- |
| `ok` | The call did what it was asked. |
| `not_found` | The thing named does not exist, or no longer does. |
| `invalid` | An argument is out of range or of the wrong kind. |
| `busy` | The game or another mod is using this right now. Try again later. |
| `not_ready` | The game is not in a state where this can happen, such as before a world is loaded. |
| `capacity` | A stated limit was reached. |
| `unsupported` | The thing exists but has no such behavior, such as a creature that never sleeps. |
| `io` | An input or output operation failed, such as reading saved data or sending a network message. |
| `denied` | The thing belongs to another mod. |
| `no_memory` | There is no memory left for it. Any call that makes or keeps something can fail this way. |

Some functions look up something that might not exist, like a squad's leader. When there
isn't one, they return `ok` with a zero handle in C, `nil` in Lua, or `null` in JavaScript.
